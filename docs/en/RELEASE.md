# Release Procedures (RELEASE.md)

This document defines the release procedures, version synchronization rules, and the operation of the automated packaging pipeline for "SnippetFlow" (Template Clipboard Manager).

---

## 1. Version Control and Automatic Synchronization Rules (SSOT)

This project consists of a frontend (React / TypeScript) and a desktop backend (Rust / Tauri). To prevent version divergence and inconsistency, please strictly adhere to the following rules.

### 1.1. Single Source of Truth (SSOT)
The source of truth for version information is **`package.json`** in the root directory. Version displays in the frontend are loaded dynamically from `package.json`. Additionally, `src-tauri/tauri.conf.json` automatically references `"version": "../package.json"`.

### 1.2. Files Requiring Manual Synchronization
Versions are not automatically synchronized between Node.js (`package.json`) and Rust (`src-tauri/Cargo.toml`). When releasing a new version, **be sure to manually update the following files to the same version**:

1. **`package.json`** (`"version"` field)
2. **`src-tauri/Cargo.toml`** (`version` field)
3. **`README.md` / `README_JA.md`** version status badges at the top

> [!WARNING]
> Any version mismatch may cause build errors or failure in creating draft releases on GitHub Actions.

---

## 2. Automated Release Pipeline (CI/CD)

This project defines an automated build and packaging pipeline (`release.yml`) using GitHub Actions.

### 2.1. Trigger Conditions
Triggered when a Git tag in the format of **`v*`** (e.g., `v1.15.0`) is pushed to GitHub.

### 2.2. Artifacts Generated by the Pipeline
Build jobs run on Windows environment (`windows-latest`), and a draft GitHub Release is automatically created with the following artifacts uploaded:

* **Tauri Version Installer**: Installers in `.msi` and `.exe` formats (built using NSIS / WiX, with Japanese wizard support).

---

## 3. Specific Release Steps

The steps to perform an actual release are as follows:

### Step 1: Quality Check and Pre-verification
Verify that the target commit passes local tests.
```bash
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
npm run lint
npm run build
```

### Step 2: Update Version Information
Update the `version` fields in `package.json`, `src-tauri/Cargo.toml`, and the badges in `README.md` / `README_JA.md` to the new version, and commit the changes.

### Step 3: Organize CHANGELOG.md
Add the new version and date section (e.g., `## [1.15.0] - 2026-09-07`) in `docs/ja/CHANGELOG.md` and `docs/en/CHANGELOG.md`, and finalize the change log.

### Step 4: Create and Push Git Tag
Commit the version changes locally, tag them, and push them to GitHub.
```bash
# Commit changes
git add .
git commit -m "chore: Bump version to v1.15.0"
git push origin main

# Create and push tag
git tag -a v1.15.0 -m "Release v1.15.0"
git push origin v1.15.0
```

### Step 5: Monitor Automated Build
Wait for the `Release Build` workflow to complete successfully (green status) in the GitHub `Actions` tab.

### Step 6: Verify and Publish Draft Release
1. Once the workflow is complete, check that a draft for the corresponding version has been generated on the GitHub Releases page.
2. Verify that installer assets (`.msi` and `.exe`) are present.
3. Write/format the release notes (copied from CHANGELOG) and click "Publish release" to publish the release.
